# 安全日志与告警缺失 · 参考解答

## 目标与实现边界

靶机 `/audit` 声明策略：“失败应记录，连续三次失败应告警”，但实际始终返回空的 failed_logins 和 alerts。教学 PIN 只有 00、01、02、03 四个候选。短 PIN 是认证弱点，本实验的核心还包括**失败后审计与告警没有变化**。

## 复现步骤

1. 先访问 `/audit`，记录空数组及策略内容，作为审计基线。
2. 按 00、01、02 各提交一次 PIN。每次预期 HTTP 403 与“验证失败”。
3. 再次读取 `/audit`。尽管已发生三次失败，两个数组仍为空，这才是日志与告警缺口的直接对照。
4. 提交最后的候选 03，预期 HTTP 200 和本次 Flag，提交到平台。

```bash
TARGET='http://TARGET_IP:8000'
curl -sS "$TARGET/audit"
for PIN in 00 01 02; do
  curl -sS -i "$TARGET/pin" --data-urlencode "pin=$PIN"
done
curl -sS "$TARGET/audit"
curl -sS -i "$TARGET/pin" --data-urlencode 'pin=03'
```

## 预期现象与常见误区

保留 PIN 的前导零，`3` 不等于字符串 `03`。本场景不需要大字典或高频扫描；四个候选已经明示。直接提交 03 虽然可以取得 Flag，却不能展示“连续失败未记录、未告警”的证据链。

平台自己的操作采集与靶机的 `/audit` 是两套不同记录：平台记录到了你的点击或命令，不代表靶机已正确记录登录失败。一次空审计结果也不能单独证明缺陷，需要先确认相应失败事件确实发生。

## 修复思路与回归

在认证结果产生处记录必要的账户标识、时间、请求关联信息与成功/失败结果，集中收集并保护日志完整性；根据策略累计失败并产生可处置的告警。不要记录明文 PIN、密码、令牌或 Flag。限速和强化认证应另行实施，它们不替代审计与响应。

回归：一次失败出现一条相应审计事件；达到三次失败条件时产生告警；重复请求按真实事件处理，避免技术重试导致重复告警风暴；正常登录保留必要结果，敏感值不入日志。

## 本实验评估要点

必须区分“猜中了 PIN”和“证明日志缺失”。重点核实失败响应、前后审计结果、预期告警规则与实际差异。若采集只有三次提交但没有响应或审计正文，不能自动判定三次失败及告警缺失已被验证，应标出待补证据。
