# 不安全设计：重复核销优惠券 · 参考解答

## 目标与实现边界

钱包初始余额 0，礼品价格 100，WELCOME 券面额 50，业务规则规定每人只能使用一次。服务端用 `wallet` Cookie 区分钱包，但兑换时只加余额，没有“已核销”状态。所有输入都可以是合法值，仍会违反业务约束。

## 复现步骤

1. 在同一个浏览器中访问 `/balance`，确认余额 0；余额不足时购买不会出现 Flag。
2. 在首页兑换一次 WELCOME，确认余额变为 50。按规则此时仍买不起售价 100 的礼品。
3. 再次提交同一张券，观察余额达到 100，而不是拒绝重复兑换。
4. 点击购买礼品，正文返回本次 Flag，再提交到平台。

终端操作必须保存并回传**同一 Cookie**。下面用临时 cookie jar 创建独立钱包，避免与浏览器状态混用：

```bash
TARGET='http://TARGET_IP:8000'
JAR=$(mktemp)
curl -sS -c "$JAR" -b "$JAR" "$TARGET/balance"
curl -sS -c "$JAR" -b "$JAR" "$TARGET/buy" -d ''
curl -sS -c "$JAR" -b "$JAR" "$TARGET/redeem" --data-urlencode 'coupon=WELCOME'
curl -sS -c "$JAR" -b "$JAR" "$TARGET/buy" -d ''
curl -sS -c "$JAR" -b "$JAR" "$TARGET/redeem" --data-urlencode 'coupon=WELCOME'
curl -sS -c "$JAR" -b "$JAR" "$TARGET/buy" -d ''
rm -- "$JAR"
```

## 预期现象与常见误区

余额轨迹应是 0 → 50 → 100，购买成功后扣减 100。重复购买不会无限返回 Flag。若每次兑换都只有 50，先检查是否丢失 Cookie、换了浏览器会话，或重置了环境。

浏览器已有兑换记录时初始余额可能不为 0；应说明已有状态，或用新的 Cookie 钱包建立干净基线。重复点击在本场景中可能产生**真实重复核销**，这是业务事实，不能在评估前简单去重；也不能仅凭双击事件就断定服务器加了两次钱，仍需结果证据。

## 修复思路与回归

为用户与优惠券建立唯一核销记录；校验、写入核销记录、增加余额放在同一事务中。并发情况下使用数据库唯一约束等保证最多生效一次，不能仅在页面禁用按钮或先查询再无约束写入。

回归：首次兑换增加 50；相同用户的顺序重复和并发重复都不再增加；不同用户按规则可以各兑换一次；购买余额不足被拒绝，成功购买只扣款一次。

## 本实验评估要点

关注同一钱包、一次性规则、两次核销及余额/购买结果，而非具体点击次数。需解释为什么这是业务状态设计缺陷，以及为什么正常字符串过滤无法修复。允许使用干净钱包重做，合理试错不扣分。
