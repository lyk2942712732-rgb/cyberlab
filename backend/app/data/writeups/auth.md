# 认证失效：账户恢复绕过 · 参考解答

## 目标与实现边界

本场景的账户恢复接口只接收 username，未要求旧密码、邮箱验证码或一次性恢复令牌。它用返回敏感资料模拟“恢复后访问账户”的影响，不会实际修改其他服务的密码，也没有完整的邮件恢复流程。

## 复现步骤

1. 首页保持 `username=student`，点击“找回账户”。预期显示普通用户恢复完成，并提示管理员用户名为 admin。
2. 比较请求参数，确认没有证明账户归属的令牌或其他凭据。
3. 只把用户名改为 `admin`，再次提交相同恢复接口。预期直接得到本次 Flag。

```bash
TARGET='http://TARGET_IP:8000'
curl -sS "$TARGET/reset-password" --data-urlencode 'username=student'
curl -sS "$TARGET/reset-password" --data-urlencode 'username=admin'
```

4. 保存普通用户与 admin 请求的差异、返回结果，提交 Flag，并指出安全边界在哪里失守。

## 预期现象与常见误区

接口需要 POST。这里两种用户名都可能返回 HTTP 200，应检查正文差异，不能把 200 等同于拿到管理员权限。知道用户名不代表拥有账户；公开用户名不能作为找回认证凭据。

与“越权访问订单”不同，那里是已知访问身份缺少对象授权；这里是恢复流程根本没有证明请求者拥有目标账户。不要只写“输入 admin 就成功”，应解释为什么恢复旁路需要独立的认证保障。

## 修复思路与回归

由可信渠道向账户所有者交付高熵、短时、一次性且绑定账户及用途的恢复令牌；验证后才允许重设。限制申请与验证频率；成功恢复后撤销旧会话；申请页面使用一致响应减少账户枚举。

回归：单独知道 admin 用户名不能完成恢复；错误、过期、已消费、属于其他账户或其他用途的令牌均被拒绝；有效令牌只能完成一次；正常持有者仍可恢复账户。

## 本实验评估要点

核实普通账户与 admin 对照、缺少身份凭据的请求结构以及敏感结果。接受等价 HTTP 工具，不要求猜测用户名（题目已经明确提供）。只有提交 username=admin 的记录不能证明收到敏感资料；需要页面、响应或判题证据补足结果。
