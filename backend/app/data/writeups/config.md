# 配置错误与备份泄露 · 参考解答

## 目标与实现边界

本场景把调试配置备份暴露在 Web 可访问路径，并在 `robots.txt` 中给出路径线索。`robots.txt` 只是对爬虫的约定，不是服务器访问控制。根因是备份文件可被未授权读取，而不是文件名本身不够隐蔽。

## 复现步骤

1. 先访问实验首页，确认它没有直接给出配置或 Flag。
2. 打开 `/robots.txt`，观察 `Disallow: /backup/config.json`。
3. 在同一靶机访问该路径。预期看到 `debug: true` 和 `training_secret`，后者为本次教学 Flag。
4. 记录发现路径的线索、实际可读取的配置及对应请求，再提交 Flag。

```bash
TARGET='http://TARGET_IP:8000'
curl -sS "$TARGET/robots.txt"
curl -sS "$TARGET/backup/config.json"
```

## 预期现象与常见误区

`robots.txt` 是纯文本；配置结果在本靶机中通过 HTML 页面展示，虽然路径以 `.json` 结尾，也不能假定响应一定是 JSON MIME 类型。能读到实际配置正文才证明泄露，单看 Disallow 不足以判断文件存在或可访问。

删除 robots.txt 中的线索、修改文件名、关闭目录列表，都不会阻止别人访问一个已知的备份 URL。该场景不需要穷举目录，也未提供可利用的调试控制台。

## 修复思路与回归

将备份和敏感配置移出 Web 根目录；由需要它的受控进程按最小权限读取；生产环境关闭调试；发布流程检查是否夹带备份文件。若敏感值已真实暴露，还需要更换对应凭据，单纯删文件不能撤销既有泄露。

修复后的部署验收：已知备份 URL 不再返回配置内容（404 或按策略拒绝）；正常首页仍可访问；生产产物中没有备份或调试配置；robots.txt 不被当成权限校验。

## 本实验评估要点

检查是否从 robots 线索到达实际备份、是否指出读取到的敏感字段，以及能否解释“隐藏路径”和“禁止读取”的区别。不要把访问 robots.txt 本身判为泄露成功；需要备份正文或对应平台判题结果支持最终结果。
