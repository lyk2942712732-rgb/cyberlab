# 异常处理失当：失败时放行 · 参考解答

## 目标与实现边界

保险箱接口把 policy_version 转成整数，再查找策略字典；版本 1 和 2 都拒绝当前用户。但是 ValueError 或 KeyError 被捕获后，代码却把 allowed 设为 True，形成“检查失败反而授权”的 fail-open 行为。

## 复现步骤

1. 首页使用 `policy_version=1` 打开保险箱。预期 HTTP 403 和“策略拒绝访问”。
2. 保持同一请求路径，把版本改为不能转成整数的 `oops` 再提交。预期 HTTP 200，正文返回本次 Flag。
3. 可再比较正常整数版本 2 与不存在的整数 999：前者仍拒绝，后者因字典查找异常也会进入错误授权分支。这一步是可选的等价成因验证。

```bash
TARGET='http://TARGET_IP:8000'
curl -sS -i "$TARGET/vault" --data-urlencode 'policy_version=1'
curl -sS -i "$TARGET/vault" --data-urlencode 'policy_version=oops'
```

4. 保存正常与异常输入的响应差异，提交 Flag，并解释不是“oops 代表管理员”，而是它触发了错误处理路径。

## 预期现象与常见误区

仅看到错误或服务器异常不能证明绕过；必须看保护资源是否返回。字符串 `2` 是有效策略且仍拒绝，不能误当成绕过值。缺少参数也可能导致解析错误，但应解释触发的分支，不把偶然结果当作特殊密码。

本靶机模拟的是解析和字典查找异常，不包含真实外部策略服务，不能声称本次已经测试了服务超时。

## 修复思路与回归

先校验输入格式与允许的版本，再执行权限判断。无效值返回受控的 400，或按统一策略安全拒绝；任何权限检查错误都不能把 allowed 设为 True。保留必要错误类别日志，不向客户端泄露内部堆栈。

回归：合法但无权的版本仍返回拒绝；非整数、缺失参数、未知版本均不返回保护内容；正常有权路径（若后续加入）仍可使用。若实际系统依赖外部策略服务，还应额外覆盖超时和不可用时的拒绝行为。

## 本实验评估要点

重点是有效输入拒绝、异常输入放行的反常对照及异常分支的解释。接受触发相同错误授权路径的非整数或未知版本。只有异常参数提交记录，而没有保护内容或判题证据时，结果应标为待核实。
