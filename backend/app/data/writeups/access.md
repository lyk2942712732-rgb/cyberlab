# 越权访问与对象授权 · 参考解答

## 目标与实现边界

靶机首页将访问者视为 alice，订单 1001 属于 alice，1002 属于 bob。这个简化场景没有完整的登录/账户切换流程；漏洞位于 `/orders` 读取对象时缺少所属关系校验。要证明的是同一个访问者可以读到其他用户的订单，而不只是编号可预测。

## 复现步骤

1. 打开首页的“查看我的订单”，检查 `/orders?id=1001`，记录响应中的 `owner=alice` 和教材信息，建立授权访问基线。
2. 只把 id 改为 `1002`，其余访问条件保持不变。响应变为 `owner=bob`，并在 `delivery_note` 中出现本次实验 Flag。
3. 记录两次请求及 owner 的变化，再提交 Flag。无需扫描一串编号，更不需要访问实验以外的系统。

等价终端操作：

```bash
TARGET='http://TARGET_IP:8000'
curl -sS "$TARGET/orders?id=1001"
curl -sS "$TARGET/orders?id=1002"
```

## 预期现象与常见误区

- 两个响应均可为 HTTP 200；关键证据是相同访问者读取了不同 owner 的数据。
- 不存在的 id 会显示“订单不存在”，不能作为越权成功证据。
- 这里的结果是订单 JSON 被包在 HTML 的 `pre` 中，不能直接把完整响应交给 JSON 解析器。浏览器或直接查看响应正文即可。
- 隐藏链接、前端禁用按钮、把编号改成 UUID 只能降低发现机会，不能替代服务端授权。

## 修复思路与回归

在服务端从可信认证上下文取得当前用户，并将订单 ID 与 owner 一起约束，例如 `WHERE id = ? AND owner_id = ?`。不要接受客户端传来的 owner 作为授权依据；管理权限需要独立校验。

回归至少覆盖：alice 访问自己的订单成功；alice 访问 bob 的订单返回 403，或按统一策略返回 404；bob 访问自己的订单成功；未认证请求被拒绝。不同错误策略应保持一致，避免泄露对象是否存在。

## 本实验评估要点

要求正常订单与其他用户订单的对照证据、相同访问身份，以及缺少对象级授权的解释。仅访问 1002 或只提交 Flag 不足以证明理解 owner 边界。接受浏览器改 URL、curl 等等价路径，不要求访问顺序完全相同；偶然重复点击不扣分。
